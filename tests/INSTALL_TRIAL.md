# Unfamiliar-User Trial

Status: not performed. This card is a procedure for a real person who did not
build the app, not a developer test result. The production goal includes a
hosted, account-backed trial. The current local app does not satisfy that gate.

## Before The Trial

The owner supplies the approved staging URL and test-account funding, or the
approved local package and README for a separate install trial. Repository access
and paid execution must be authorized first. Hosted users must not be asked for
worker or provider secrets. Local testers use their own authorized backend
credentials, never a key copied into chat or a bug report. Record a spending
ceiling and image/video job counts first; without them, stop before generation.
Use original or permissioned inputs, including generated fictional characters
if needed. Do not use the private human-reference experiments as trial assets.

## Task

Use only the README and the running app. The maintainer observes without coaching.
Stop if a step would disclose a secret, exceed the allowance or risk duplicate
spending. Record where help was needed rather than silently filling the gap.

1. Open the approved hosted app and sign in without provider keys, or install
   and launch the clean local package. Record which path was tested; the latter
   does not prove hosted account/billing readiness.
2. Create a named vertical or square project. Choose the assigned starting mode
   and provide its idea or permissioned image/audio/video. Find the scene and
   reference controls without help. Uploads must meet the displayed limits.
3. Choose a scene, add or generate an opening image where relevant, and review
   it. Find Use opening at end and explain what you expect it to change. Changing
   this setting must not generate another image or video.
4. Check the hosted price/ceiling and explicitly generate one LTX take. Record
   actual charge, runtime and creative quality once it completes.
5. Reload during a pending job once. Recover that same job if requested; do not
   create a replacement for an unknown outcome. After it completes, review the
   result, play it and scrub to a time.
6. Make a meaningful revision. Change the scene/reference or advanced motion
   direction, and generate another take only within the approved allowance.
   Return to the first take; its result, references, directions and seed must
   remain. Compare alternatives and explicitly choose one for the short.
7. Add/reorder enough shots for a short sequence, within the preapproved job
   count. Add a supplied soundtrack and at least one caption. Select the intended
   take for each shot, trim a shot and export the finished short.
8. Reload/reopen the project and verify shot order, references and selected takes.
   Open the MP4 outside the app; verify framing, sound, caption placement and
   intended cut order. Export the editable project/assets, import it as a separate
   project and make a revision. Missing portability is a failure, not a passed
   gate based only on the same-server edit manifest.
9. For the hosted trial, sign out and back in to the same account. Confirm the
   project and balance/charges persist. Do not request a second identity or test
   someone else's private links without separate approved test accounts.

Do not ask the tester to run developer tests or understand SDK internals. Record
installation time and hands-on time separately from provider queue/render time.
If a first result fails creatively, keep it in the report; do not keep spending
until the trial appears successful.
